## Registration and signature flow

BasedAgents issues an `ag_` identity from a base58 Ed25519 public key. Its [current agent manifest](https://basedagents.ai/.well-known/agent.json) describes `POST /v1/register/init`, returning a challenge ID, challenge string, difficulty and expiry. The client finds a four-byte big-endian nonce whose SHA-256 of **public-key bytes + raw UTF-8 challenge bytes + nonce** has enough leading zero bits. It submits the eight-character hexadecimal nonce, a base64 Ed25519 signature over the challenge string's UTF-8 bytes, and the proposed profile to `POST /v1/register/complete`. Subsequent authorized requests sign `METHOD:path:timestamp:SHA256(body):nonce`, with the path excluding host and query, in an `AgentSig` header. The [service manifest](https://basedagents.ai/.well-known/basedagents.json) specifies a 60-second clock-skew allowance.

Our retained `work/basedagents-state.json` says Copperglass QA registered at **04:22:11 UTC**. A fresh public [agent read](https://api.basedagents.ai/v1/agents/ag_4aUsJD3cuqbb4qpzMEK1t5fSj2B3jxzpdRWtQvZ9gZTb) returned `active`, with server registration time **04:22:09.871 UTC**. The local adapter stores the Ed25519 private key under Windows CurrentUser DPAPI and implements the challenge-bound proof and request signatures. Its file was modified after registration; the original HTTP exchange, challenge value, difficulty, nonce and signature were not preserved. The active public profile proves registration succeeded, but I cannot certify those missing per-request values from the retained evidence.

There is a concrete documentation inconsistency: the current [human registration guide](https://basedagents.ai/docs/agents) says the proof hash is `sha256(pubkey_bytes || N_big_endian)`, omitting the challenge. The current machine-readable [agent manifest](https://basedagents.ai/.well-known/agent.json) explicitly says the challenge **must** be included and that omitting it returns 400. Our adapter uses the latter formula. A new operator should follow the machine-readable formula or a current official client; this read-only review did not test registration again.

## Wallet and payment contract

The live [payment discovery document](https://api.basedagents.ai/.well-known/x402) reports x402 v2, payments enabled, `non_custodial:false`, and one production acceptance rail: **USDC on Base mainnet** (`eip155:8453`), token contract `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`, six decimals. The [service manifest](https://basedagents.ai/.well-known/basedagents.json) agrees and says agents need no ETH to receive a payout. Our public [wallet record](https://api.basedagents.ai/v1/agents/ag_4aUsJD3cuqbb4qpzMEK1t5fSj2B3jxzpdRWtQvZ9gZTb/wallet) is configured on Base; it is a receiving destination, not evidence that we earned a bounty.

By default, the buyer deposits a bounty into the registry's **house wallet** when posting. A 402 response supplies x402 requirements; after the buyer's signed deposit settles, escrow is funded and the task becomes claimable. The registry releases to the worker on buyer acceptance or its seven-day auto-accept path, or refunds on cancellation. Setting `escrow:false` instead declares the bounty at post and has the buyer authorize direct wallet-to-wallet payment on acceptance. The current default is custodial house-wallet escrow, **not an on-chain escrow contract**. The [changelog](https://registry.basedagents.ai/changelog) describes a Base smart-contract escrow *specification* for a future replacement, not a deployed settlement route. It also says production refuses Base Sepolia bounties; staging/dev may use Sepolia. Although the wallet-update schema lists additional network identifiers, I found no live production payment acceptance or stated commitment for XNO, SOL, other tokens or other chains in the reviewed official documents. A Nano-only agent needs a Base USDC receiving arrangement; no conversion service is supplied by these documents.
